# ADR-007: 扩展入口统一为网页浮层

## 状态

Implemented

## 背景

EchoMem 曾尝试把浏览器原生 Side Panel 作为工具栏主入口，同时保留网页 overlay。实际使用时，两套界面可能并排出现，造成重复导航；原生 Side Panel 还会压缩 HIGO 的主内容宽度。输入框附近的旧按钮又依赖会话和输入框出现，入口位置不稳定。

## 决策

EchoMem 只保留网页 overlay 作为完整功能容器：

1. 点击浏览器工具栏图标，Background 向活动标签页发送 `openEchoMemOverlay`。
2. Content Script 收到消息后，在已识别的支持平台上调用幂等入口 `ensureEchoMemOverlayOpen()`。
3. HIGO 标题栏保留“图形 + EchoMem”组合标，并使用同一个幂等入口。
4. 删除聊天输入框附近的 EchoMem 按钮，不再依赖输入框生命周期提供入口。
5. 删除 Side Panel 权限、页面、脚本、路由、构建产物和发行文件。
6. overlay 的结构、样式、功能路由和关闭行为保持不变。
7. overlay 已打开时，再次点击任一入口保持当前实例和当前功能页，不重复创建或重置路由。

## 入口模型

```text
浏览器工具栏图标 ─┐
                  ├─> Content Script ─> ensureEchoMemOverlayOpen()
HIGO 标题栏组合标 ─┘                         │
                                             ├─ 已打开：保持当前实例
                                             └─ 未打开：openEchoMemHomePanel() ─> 网页 overlay
```

工具栏入口依赖活动标签页已加载 Content Script 且平台检测成功。浏览器内部页面或未支持页面不创建 overlay。

## 结果

- 页面最多出现一个 EchoMem 功能容器，不再出现 overlay 与 Side Panel 并排。
- 打开 EchoMem 不改变宿主页面布局宽度。
- 未进入会话时，HIGO 标题栏组合标仍可使用。
- 输入联想、内容插入和会话录制仍可继续查找平台输入框，但不再为此注入入口按钮。

## 未采用方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 浏览器原生 Side Panel | 删除 | 挤压宿主页面，并与 overlay 形成重复功能容器 |
| 工具栏 popup 承载完整功能 | 不采用 | 空间有限，失焦即关闭，不适合多级功能 |
| 输入框附近按钮 | 删除 | 依赖会话和输入框出现，位置突兀且入口不稳定 |
| HIGO 标题栏组合标 + overlay | 采用 | 不挤压页面，入口稳定，并能复用现有完整功能 |

## 验收标准

1. Manifest 不声明 `sidePanel` 权限和 `side_panel` 页面。
2. 点击扩展工具栏图标向活动标签页请求打开 overlay。
3. HIGO 标题栏显示“图形 + EchoMem”组合标，并打开同一 overlay。
4. HIGO 和 DeepSeek 输入框附近均不再出现 EchoMem 按钮。
5. 现有 overlay 的 DOM、样式、路由和业务功能不因本决策改变。
6. 构建和发行包不包含 Side Panel 文件。
