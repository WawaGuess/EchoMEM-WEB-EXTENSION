# ADR-004: 模块化内容架构

## 状态
Accepted / Implemented

## 背景

改造前，Chrome 实际加载的是根目录 `content.js`，它同时包含平台配置、平台检测、入口注入、面板系统、功能面板、导航和状态逻辑。`src/` 虽然已有模块化拆分，但还没有成为运行入口，存在两个维护压力：

1. 运行真相在 `content.js`，模块化源码在 `src/`，后续改动容易产生漂移
2. 新增平台或功能面板时，需要同时理解注入、面板、导航、状态和平台配置，扩展成本越来越高

## 决策

采用"单一源码入口 + 构建输出 + 注册机制"的架构：

- `src/entry/content.js` 作为唯一源码入口
- `dist/content.js` 作为构建产物，Chrome 实际加载
- 建立 `platformRegistry` 和 `panelRegistry` 注册机制
- 新增平台或功能面板变为局部改动

## 目录结构

```text
src/
├── entry/content.js      # content script 源码入口
├── core/                 # 检测、注入、路由、状态、面板承载
├── panels/               # 功能面板模块
├── platforms/            # 平台注册表和配置
└── services/             # Chrome API 包装层
```

## 备选方案

| 方案 | 拒绝原因 |
|------|---------|
| 继续维护根目录 content.js | 双线维护，源码与运行入口漂移 |
| 引入 React/Vue 框架 | 过度设计，增加打包体积和复杂度 |
| 使用 webpack 替代 esbuild | esbuild 足够轻量，构建速度快 |

## 影响

1. `src/entry/content.js` 成为唯一源码入口
2. `manifest.json` 的 `content_scripts.js` 指向 `dist/content.js`
3. 新增平台只需在 `src/platforms/` 添加配置并在 `platformRegistry` 注册
4. 新增功能面板只需在 `src/panels/` 实现并在 `panelRegistry` 注册
5. 构建命令：`npm run build`（esbuild 打包）

## 相关代码

- `src/entry/content.js`
- `src/platforms/index.js`
- `src/panels/registry.js`
- `manifest.json`
